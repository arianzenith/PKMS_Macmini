1. 거대 가설

인터페이스의 주권 이전: LLM 에이전트의 부상은 시스템 인터페이스의 패러다임을 GUI(인간용)와 API(기계용)의 이원 체제에서 CLI(공용어) 중심의 단일 체제로 회귀시킨다. 과거 CLI는 전문가의 전유물이었으나, 이제는 자연어로 CLI를 능숙하게 다루는 LLM 덕분에 가장 보편적이고 효율적인 소통 방식이 된다. 이 현상은 소프트웨어 개발의 본질이 ‘기능 구현’에서 ‘명령어 체계 설계’로 이동하고 있음을 시사한다. 단기적으로 기업 내 개발팀은 AI 에이전트 연동을 위해 별도의 API를 구축하는 대신, 기존의 관리용 CLI를 그대로 노출하거나 신규 제작하는 방향으로 전환할 것이다. 이는 개발 리소스를 절감하고, 인간과 AI가 동일한 도구로 협업하는 환경을 구축해 디버깅 비용을 극적으로 낮춘다. 장기적으로는 기업의 기술적 해자(moat)가 독점적인 GUI나 복잡한 API 생태계가 아닌, 얼마나 직관적이고 강력하며 조합하기 쉬운 CLI 명령어를 제공하는가에 따라 결정될 것이다. 마치 레고 블록처럼, 가장 뛰어난 CLI를 제공하는 서비스가 전체 AI 에이전트 생태계의 기판(motherboard) 역할을 차지하게 된다.

2. 충돌 지점

AI-Native의 자기모순: 현재 시장은 ‘AI-Native’ 솔루션을 부르짖으며 LLM을 위한 새로운 인터페이스(MCP)와 전용 아키텍처를 구축하는 데 열을 올린다. 이는 LLM을 특별하고 새로운 존재로 간주하여 격리된 환경을 제공하려는 시도다. 하지만 이 소스는 정반대의 관점을 제시한다. LLM의 진정한 능력은 새로운 환경에 적응하는 것이 아니라, 수십 년간 축적된 인간의 가장 강력하고 원초적인 인터페이스인 CLI를 즉시 이해하고 활용하는 데서 발현된다는 것이다. MCP와 같은 ‘AI 온실’을 구축하는 것은 오히려 LLM의 잠재력을 제한하는 족쇄다. 이는 AI 시대를 맞이하는 우리의 접근법이 근본적으로 잘못되었을 수 있다는 지적과 충돌한다. 우리는 AI를 위해 새로운 운동장을 만들 것이 아니라, 기존 프로 선수들이 뛰는 운동장에 AI를 바로 투입해야 그 진정한 가치를 발견할 수 있다.

안정성의 역설: 중앙화된 MCP 서버는 단일 지점에서 모든 것을 통제할 수 있어 더 안정적이고 관리하기 쉬울 것이라는 직관적 믿음이 존재한다. 반면, 개별적으로 실행되는 CLI는 분산되어 있어 통제가 어렵고 불안정할 것이라 여겨진다. 소스는 이 통념을 완전히 뒤집는다. 상태(state)를 가져야 하는 MCP 서버는 필연적으로 프로세스 관리가 필요하며, 이는 곧 장애 포인트의 내재화를 의미한다. 반면 상태가 없는(stateless) CLI는 각 실행이 원자적(atomic)이고 독립적이기에 시스템 전체의 안정성을 해치지 않는다. 즉, 통제를 위한 중앙화 시도가 오히려 시스템 전체의 취약성을 높이는 역설이 발생한다. 진정한 안정성은 통제 가능한 단일 실패 지점을 만드는 것이 아니라, 실패가 전파되지 않는 무수한 독립 실행 단위를 확보하는 데서 나온다.

3. 창발 아이디어

CLI 우선주의 선언 및 내부 표준화: 오늘부터 모든 신규 내부 도구 및 자동화 스크립트 개발 시 ‘CLI-First’ 원칙을 적용한다. 개발팀은 GUI나 별도 API 엔드포인트를 만들기 전에, 반드시 해당 기능의 핵심 로직을 수행하는 독립적이고 상태 없는 CLI를 먼저 개발하여 공개해야 한다. 이 CLI는 인간 개발자와 LLM 에이전트 양쪽 모두가 사용할 수 있도록 명확한 인자와 옵션, 그리고 표준 출력 형식을 가져야 한다. 기존에 API로만 제공되던 내부 서비스들도 CLI 래퍼(wrapper)를 제작하는 프로젝트를 시작한다. 오늘 당장 실행할 첫 단계는, 현재 사내에서 가장 자주 사용되지만 자동화가 불편했던 API 기반 워크플로우 하나를 선정하고(예: 임시 테스트 환경 생성 및 삭제), 이를 대체할 단일 CLI 툴을 이번 주 내로 프로토타이핑하는 것이다.

에이전트용 '최소 권한 셸' 환경 구축: LLM 에이전트에게 시스템의 루트 셸을 그대로 노출하는 것은 보안상 위험하다. 이를 해결하기 위해, 특정 작업 수행에 필요한 최소한의 CLI 명령어들만 화이트리스트 방식으로 포함하는 제한된 실행 환경(가칭 ‘Agent Shell’)을 컨테이너 기술(예: Docker)을 이용해 구축한다. 에이전트는 이 격리된 셸 안에서만 활동할 수 있다. 예를 들어, ‘Pull Request 리뷰’ 에이전트의 셸에는 `gh pr view`, `gh pr diff`, `git fetch` 등의 읽기 전용 명령어만 포함하고, `gh pr merge`나 `git push`와 같은 쓰기 명령어는 원천적으로 제외한다. 이는 MCP의 조악한 도구 단위 화이트리스트와 달리, 명령어 단위의 세밀한 권한 제어를 가능하게 하여 보안과 자율성 사이의 균형을 맞추는 현실적 해법이 된다.
